## How status is read

Status is derived from what this document records; nothing here is a
maintained header.

- A **question** (`L1-Qn`) is open exactly when it has no `Ruling` field.
  `Authority` is `operator`, `self-under-standing-go`, or `defaulted`.
- A **cut** is landed when its `Landed` field names commits, and closed when
  every promise (`P<cut>.<n>`) in its Verdicts table has a verdict
  (`HOLDS | FALSIFIED | UNPROVEN`). The root agent fills `Landed` and the
  Verdicts; Hands and Soul do not edit this file.
- A **mutation** (`M<cut>.<n>`) names file, line, before and after; the commit
  it ran against is filled at execution. Mutations run against committed code
  and are restored with a diff, never `git checkout`.
- A **finding** (`L1.f<n>`) is something no cut owns; each carries
  introduced-or-pre-existing, severity, and triage (`fix | operator | recorded`).
- The **ledger** carries an estimate per cut; the Actual column is computed
  from the diff at landing and is empty until then.

The pass is open until every cut is closed and every question has a ruling.

## Questions

### L1-Q1 What seeds the lens draw

- **Asked:** 2026-09-16.
- **Context:** nothing counts sessions. The kernel's one entropy recipe is a
  digest over a typed preimage plus modulo and a cumulative walk
  (`action.rs:780-818`). Under L1-Q4 the lens enters the command id, so the
  draw cannot be seeded by the command id (it would be circular); it is
  seeded by the identity fields the command id is derived from.
- **Options:** A: seed from the session identity — `LensPreimage {
  world_id, jurisdiction, answer_digest }` (the same fields
  `session_command_id` hashes before the lens joins) digested with the
  kernel's `sha256:` recipe, first sixteen hex as `u64`, modulo the weight
  total, cumulative walk in `Lens` order; the draw is a pure function of
  (world, answer identity, weights). B: a new session ordinal counted
  somewhere; requires a counter owner and a write per session. C: the
  snapshot revision at session start; not replayable across resume without
  recording it, which is A with an extra field.
- **Recommendation: A**, because it introduces no counter, reuses the one
  recipe, and makes "the same session identity draws the same lens" true by
  construction. Replayability, not determinism of model output, is the
  invariant.
- **Depends on it:** Cut 1 (`lens::draw`), Cut 3 (draw site).
- **Ruling:** A. The operator: "I couldn't care less what seeds the lens draw
  as long as it's replayable - deterministic generation is out of reach
  regardless." The seed is chosen on engineering grounds as A; the preimage
  was amended from `{world_id, command_id}` to the identity fields when
  L1-Q4 put the lens into the command id (same authority, same day).
- **Authority:** self-under-standing-go.
- **Ruled:** 2026-09-16.

### L1-Q2 Where weights live and how they are admitted

- **Asked:** 2026-09-16.
- **Context:** `WorldState` has no `deny_unknown_fields` (`lib.rs:780`); the
  only genesis-written world scalar is `scale_intent` (`lib.rs:845`),
  validated in `resolve_patch` (`patch.rs:4597-4615`) and re-checked at

  and by length at `:1771`, and older stores are refused (`journal.rs:473`,
  `:1245`).
- **Options:** A: `WorldState.lens_weights: LensWeights` beside
  `scale_intent`, written by genesis through `ResolvedPatch.lens_weights:
  Option<LensWeights>` exactly as `scale_intent` is, carried on `CreateWorld`

- **Recommendation: A.**
- **Depends on it:** Cut 2.
- **Ruling:** A. The operator: "Lens weights live in the world, they're what
  determine the flavor of the world after all."
- **Authority:** operator.
- **Ruled:** 2026-09-16.

### L1-Q4 How concurrent sessions stay distinct and take controller permits

- **Asked:** 2026-09-16.
- **Context:** probe 1 above. `sweep` is a sequential loop over
  jurisdictions (`elaboration.rs:607-632`); `select_answer` (`:642-677`)
  picks one answer per jurisdiction per call — the oldest boundary, else the
  deficit — so two runners on one jurisdiction pick the same answer. The
  runtime holds no permit for the sweep; today one pool serves speak turns
  and cover cells (`runtime.rs:1080-1082` "There is no second concurrency
  owner").
- **Options as posed:** A: claim distinct demand, identity unchanged, the
  sweep borrows Dungeon's single pool. B: a slot ordinal in the identity. C:
  A plus deficit slots. D: both — the lens in the identity and a per-sweep
  claim set — with the pool split.
- **Ruling: D.** The operator: "Both, split the pool. Neither elaboration nor
  simulation should starve the other. Elaboration pool is a ceiling, not a
  budget like the Simulation pool." Read as:
  - **Both.** The drawn lens enters the session's command identity:
    `session_command_id` = `CommandId::derived(ELABORATION_NAMESPACE,
    [scope, answer_digest, lens.name()])`. And the runner hands concurrently
    running sessions distinct demand entries: `demand_entries(snapshot)`
    enumerates every open boundary per jurisdiction plus one deficit per
    jurisdiction with a nonzero row, draws each entry's lens, derives each
    id, and dedups by id. That claim set is an in-memory value rebuilt each
    sweep — scheduling state, never world state, never persisted.
  - **Split the pool.** Dungeon carries two `Semaphore`s: the existing
    `controller_permits` becomes the **simulation pool** (speak turns at
    `runtime.rs:1082`, cover cells at `:1975`), configured by
    `GHOSTLIGHT_CONTROLLER_MAX_CONCURRENT` (default 4, unchanged); a new
    `elaboration_permits` is the **elaboration pool**, configured by
    `GHOSTLIGHT_ELABORATION_MAX_CONCURRENT` (default 2, minimum 1, read at
    open beside the other, `:1866-1872` shape). `sweep(&self, permits:
    Arc<Semaphore>)` receives the elaboration pool only. Neither lane ever
    acquires from the other's semaphore, so neither can starve the other in
    this process.
  - **Budget versus ceiling.** The simulation pool is capacity simulation
    always has: no other lane draws from it. The elaboration pool is a
    ceiling: the most sessions elaboration may run at once, and nothing
    reserves that capacity for it downstream. The ceiling is enforced by the
    semaphore's size alone: a session holds one permit for its whole step
    and is spawned only after `acquire_owned` returns, so at most N
    elaboration inferences are in flight. Connector-level quota is shared
    by both pools through one caller id; when the connector refuses for
    capacity, elaboration's refusal is a retryable fault that ends the
    session's step and is retried next sweep, and simulation's is the same
    retryable fault it is today (`runtime.rs:1863-1865`). The process
    guarantees no local starvation; it cannot make the connector prefer
    simulation, and this map says so (L1.f8).
  - **Test.** `saturating_one_pool_never_delays_the_other` (Dungeon,
    `runtime.rs` tests): hold every elaboration permit in the test, run
    `run_cover_tick` on the two-cell world with a counting port, assert both
    cells ran and the tick's wall time is bounded (no wait on the held
    pool); then hold every simulation permit and run a sweep on a world with
    one boundary, assert one `infer` call completed. Library side:
    `the_sweep_never_exceeds_its_ceiling` (pool 1 → max one in flight) and
    `distinct_entries_run_at_once_under_the_ceiling` (pool 2 → max two).
- **Authority:** operator.
- **Ruled:** 2026-09-16.
- **History (superseded):** this map first recommended A — identity
  unchanged, `sweep(permits)` taking Dungeon's single pool — on the grounds
  that distinct entries alone make probe 1's collision unreachable without
  touching identity or its tests. The ruling puts the lens in the identity
  as well and splits the pool; the deficit-parallelism limit noted under A
  (one deficit session per jurisdiction per ancestry) still holds under D
  and is stated in Cut 4.

### L1-Q7 Where the lens text lives: per-lens instructions or the user turn

- **Asked:** 2026-09-16; reposed the same day after the operator asked why
  per-lens instruction strings cannot be versioned when a checkpoint
  references them. Probed (see "Probe Q7" above).
- **Context:** the checkpoint persists `agent_prompt` and the whole
  `PreparedInference` (`elaboration.rs:77-84`); `integrity_is_valid`
  rebuilds the request from the code constant and demands equality
  (`:134-170`); an edit to that constant refuses every store holding an
  in-flight row (probe, base). The sidecar places `instructions` as the
  system prompt (`main.ts:242`). Row size ≈ 58 KB, dominated by tool
  schemas.
- **Options:**
  - (a) **Per-lens instructions persisted on the session.**
    `ElaboratorSession.instructions: String` is filled once from
    `lens.instructions()` (the constant's sentence plus the lens clause)
    when the session is built; `elaboration_request` takes the text;
    `step`, `persist_repair` and `integrity_is_valid` read it from the
    session. Probed: open-time integrity, resume and the repair path all
    work, and the lens clause reaches the wire on every round.
    `provider_request_id` stays stable across resume (it hashes the stored
    text) and becomes a stable per-lens prefix across sessions of one lens
    (same text, so the connector's cache prefix is shared per lens rather
    than per world). What is lost: the stored instructions are no longer
    proven equal to current code; a row whose text was written by an older
    build, or forged, validates as long as its stored invocation agrees with
    its stored text. What is kept: the stored invocation is proven to equal
    a request rebuilt from the stored text and the stored conversation
    (request id, conversation id, tools, model, shape). Cost: about 250
    bytes per row against ≈ 58 KB (< 0.5 %); no version table; a lens-text
    edit needs no row-version bump and strands no store.
  - (b) **A version id with every historical string retained in code.**
    `ElaboratorSession.instructions_version: u32` (or `lens_text.vN`) and a
    table `LENS_INSTRUCTIONS: &[(u32, [&str; 8])]`; integrity rebuilds from
    the table entry the row names. Keeps "stored text equals code" for every
    version ever shipped, at the cost of the table growing by eight strings
    per edit forever, and a review question ("which version is live?") the
    code must answer twice.
  - (c) **A version id, rows naming a retired version refused at open.**
    The same field, one live entry; a row from a retired version fails
    integrity at open. Behaviourally this is today's rule with a named
    error, so it buys nothing over the existing row-version bump except the
    version field.
  - (d) **User turn.** The lens paragraph rides in `build_prompt` →
    `agent_prompt`, already persisted and never rebuilt; `ELABORATION_INSTRUCTIONS`
    stays one static; nothing about integrity changes; the constant keeps
    refusing stores when edited (the base hazard stays); steering is weaker
    than the system prompt and the connector's cache prefix stays one for
    every lens.
- **Recommendation: (a).** The probe did not falsify it: every path the
  question named works, and the guarantee it gives up (stored text equals
  code) was in practice the store-refusing hazard the operator was asking
  about, with the pass discipline already making it moot by bumping the row
  version. The row keeps carrying what the model actually saw, as
  `agent_prompt` already does, which is the property a resumed conversation
  needs. (b) grows code per edit; (c) is the present behaviour with a
  field; (d) is the fallback if the operator wants the instruction text
  provably equal to code, at the cost of weaker steering and no per-lens
  cache prefix. Cut 3 is written for (a) with a one-line delta for (d).
- **Depends on it:** Cut 3.

- **Context:** with the lens in the command id, a session's row is found by
  `lookup(command_id)` (`controllers.rs:1645-1668`; the store has no listing
  method). If the owner replaces the weights after a session drew and before
  it resumes, the redraw for the same answer may yield a different lens, a
  different id, and a `Missing` lookup: the old row would be stranded and a
  second session would spend inference on the same answer, against L1-Q3's

- **Options:** A: before drawing, `demand_entries` probes the eight
  candidate ids for the answer (one per lens; in-memory `BTreeMap` lookups)

  adopts that row's session (its lens and text) instead of drawing; no
  schema, no trait change, eight cheap lookups per entry. B: add
  `ControllerWorkStore::elaboration_rows()` to the trait (every store,
  including test stores, implements it) and select from the listing. C:
  accept the stranding: the old row keeps its lens (the letter of L1-Q3)
  and is never resumed.
- **Recommendation: A**, because it honours L1-Q3 without a schema or trait
  change and the store already answers `lookup` from memory.
- **Depends on it:** Cut 3.
- **Ruling:** A.
- **Authority:** defaulted — an internal lookup strategy that changes no
